Agents Don't Fail Loudly

Designing for the gap between an action and what the agent knows about it

October 20269 min read1,849 words

Suppose a customer asks for a €40 refund. An agent finds the payment, checks the policy, and calls the refund API. The request times out.

There are now two possible worlds. In one, the payment service never received the request. In the other, it issued the refund and the response was lost. The agent has the same evidence in both worlds.

If it retries carelessly, it may refund twice. If it gives up, it may leave the customer waiting for money that was never sent. If it says the refund succeeded, it may be inventing a financial event. A fluent explanation is available in every case.

This is a useful place to begin thinking about production agents. The model may have understood the customer perfectly. It may have chosen the right tool with the right arguments. We still need a design for what happens next.

The attraction of an agent is that it can work out how to do something we have described loosely. That flexibility also makes it easy to leave parts of the system undesigned. We give it a goal, some tools, and permission to continue until it believes it has finished. Then we discover that “finished” contains several decisions we never made.

The refund example is hypothetical. It is small enough to examine without appealing to anyone's production war stories, and it exposes three questions worth answering for any agent that can change something: what happened, what was allowed to happen, and what evidence would let us tell the difference?

The missing state

A first implementation might record each tool call as either successful or failed. A timeout goes into the failed column, where a retry policy picks it up.

That representation has already made a business decision. It has treated the absence of a response as evidence that no money moved.

We need an unknown state. Once a request may have reached the payment service, the workflow must preserve the possibility that the refund exists. Recovery then involves finding out what happened.

This requires a durable record of the operation before dispatch: the request identifier, payment identifier, amount, currency, and authorisation that permitted it. After dispatch, record the response or the fact that the outcome is uncertain. If the process crashes between those records, recovery should conservatively treat the operation as potentially dispatched.

These are separate durable transitions. A transaction in our database cannot generally include the payment service's remote action. Holding a database transaction open while making the call would still leave us with a possible refund and a rolled-back local record.

An outbox can help with a particular part of this design. We can commit the authorised refund request and a message requesting its execution in one local transaction. A worker then delivers that message. This closes the gap where the request is recorded but the process dies before arranging delivery. The worker can still deliver twice, so the receiver must handle duplicates appropriately. The transactional outbox pattern solves a local coordination problem; the external effect still needs its own protection.

The unknown state also needs a way to leave it. A background worker might query the provider using a recorded refund identifier or a supported operation reference. Some providers let us safely repeat the original request. Others offer too little information to resolve the ambiguity automatically.

That last case needs an owner. Give unresolved operations a deadline for escalation and preserve the evidence a person will need. An entry in an unknown column is otherwise just a customer problem hidden in a database.

What counts as the same operation?

Idempotency gives us a way to repeat a request while limiting its effect. But it depends on our definition of “repeat.”

Consider two requests to refund €40 against the same payment. They might be retries of one customer request. They might also be two separately authorised partial refunds. The payment identifier and amount cannot distinguish them.

The identifier therefore belongs to the business operation. When the application accepts a new refund request, it creates an operation identifier and persists it. Every attempt to execute that request uses the same key. A second authorised refund receives a different one. The application also has to recognise duplicate submissions of the original request; creating a fresh operation whenever the customer clicks again would move the duplication problem upstream.

The model should not invent a new key when it decides to try again. Generating fresh identifiers would allow each retry to look like a new instruction to move money.

The provider's contract matters here. For example, Stripe documents that API v1 requests using the same key return the stored result after execution begins, including stored errors. It also documents parameter checks and key retention limits. A retry policy has to respect those details. A key that has been forgotten by the receiver offers no protection against a much later replay.

Where the provider cannot deduplicate requests, our local records alone cannot guarantee a single external effect. We may be able to reconcile against its ledger. We may have to stop and ask a person. Some actions have a compensating action, but compensation is another operation that can fail. Sending a correction email does not unsend the first email.

This is why recovery behaviour belongs in the tool design. An agent should be able to distinguish an operation it can safely retry from one whose outcome it must investigate. Exposing a tool that returns a generic error throws away information the rest of the system needs.

How much should the model decide?

The refund also helps locate the useful boundary for the model.

Understanding a customer's explanation may require interpretation. The customer might describe a duplicate charge indirectly, refer to an earlier conversation, or ask for an exception. A model can help turn that account into a proposed action.

Other decisions are already specified. The authenticated account determines which payments the customer can access. The payment record determines the currency. The current refundable balance limits the amount. These facts should be enforced by the tool that executes the refund.

A useful interface might let the model propose a payment identifier, an amount, and a reason. The server resolves those identifiers within the customer's account, checks the amount against current state, and requires any necessary authorisation. The check must remain valid when the refund executes, including when another request is being processed concurrently.

This makes it possible to improve the model without making it responsible for every invariant in the application. Better understanding can reduce mistaken proposals. Server-side controls restrict what even a mistaken proposal can do.

It also makes human approval more useful. The reviewer can inspect a specific operation: this payment, this amount, this customer, this reason. If those values change after approval, the approval no longer applies. A broad instruction to “handle the customer's issue” gives the reviewer much less to assess.

There is still judgment in deciding which actions need review. The important thing is to make that a product decision with an explicit scope. We should be able to explain why an operation is permitted without relying on the model's assurance that it seems sensible.

What does the receipt prove?

Eventually the payment service returns a refund identifier. Can the agent now tell the customer that the money is back?

That depends on what the response means. The provider may have accepted the request while the refund remains pending. A receipt for acceptance supports a different statement from confirmation that processing has completed. The customer-facing language should follow the recorded status.

Even a completed refund proves only part of what we care about. The system may have refunded the wrong payment. The customer may have wanted a replacement. The amount may satisfy a policy while leaving the underlying complaint unresolved.

There are several checks here. We can check that a request was authorised, that the provider executed it, and that the result matches the intended payment and amount. Assessing whether the response was appropriate to the customer's situation may require a separate review of the conversation.

A second model can help with that review, but agreement between two models is still something to evaluate. Give the reviewer examples with known mistakes: the right amount on the wrong payment, a pending refund described as completed, an exception granted without approval. Measure which mistakes it misses. Its usefulness depends on those results.

Protect the evidence as well. A checking process offers little independence if the agent can edit its inputs or replace its implementation. Conversely, the agent can know the refund policy without gaining permission to alter the ledger against which its work is checked. The relevant boundary is what it can change.

At the product level, the same care is needed with metrics. Closing a support ticket is easy to observe, but a customer can remain unhappy after closure. If closure becomes the main success measure, inspect reopened tickets and unresolved complaints too. The refund record and the conversation answer different questions, and both belong in an evaluation of whether the work was good.

Building the first version

I would start this system with a smaller task than “resolve refund requests.”

The first version could identify the payment, explain the applicable policy, and prepare a refund for approval. It would still be useful. It would also let us observe where interpretation fails before giving the model authority to execute every proposal.

The recovery path can be tested separately. Make the payment service accept a request and then drop the response. Kill the worker after dispatch but before it records the result. Submit the same customer request twice. Try two legitimate partial refunds with equal amounts. Resume an operation after the provider's deduplication window has expired.

Each test should have an expected business outcome. For the lost response, the system should eventually establish whether the original refund occurred, using reconciliation or a retry permitted by the provider's contract. If it cannot, it should preserve the uncertainty and escalate. A test that merely checks whether the worker exited successfully would miss the problem we set out to solve.

These tests do not require an autonomous agent. That is useful: we can establish the behaviour of the execution machinery while evaluating the model's interpretation separately. Combining them later still needs testing, but a failure will be easier to locate.

Once we understand those results, we can expand the cases allowed to execute without review. The decision would be based on observed errors and the cost of a mistaken action. More autonomy would then correspond to a specific set of cases we understand well enough to permit.

An agent can make an application useful in situations its original programmers did not enumerate. The surrounding application still has to account for the actions it permits. If a customer asks where their €40 went, someone needs to be able to answer from a record of what happened.
